# Method-level issue-linked fix overlap: exploratory protocol v0.1

## Question and status

In Jenkins and Apache Tomcat, are annual-snapshot Java definitions flagged as Long Methods more likely than comparable unflagged definitions in the same production file to have their executable body modified by an issue-linked, fix-labelled commit in the following 365 days? This is an exploratory analysis devised after the aggregate, file-activity and fix-labelled file results were inspected. It cannot serve as a preregistered confirmatory test. A linked subject is a documentary proxy, not proof that the tracker issue is a confirmed defect; tracker metadata and changes must be checked before making a claim about verified bug fixes.

## Population and matching

Use the sealed annual Java syntax inventories for 2007–2024. Only complete syntax scans enter. Keep definitions with a body, a unique `(path,symbol)` at the baseline, and an eligible production-file lineage in the corrected file cohort. A finding is Long Method if the same syntax report records cyclomatic complexity >10; the finding list and threshold must agree. Exclude definitions in paths whose baseline source is unavailable or whose baseline definition record disagrees with its finding. For each flagged definition, select one unflagged definition from the same file and snapshot, without replacement, minimizing absolute difference in log(1+physical lines), with symbol order breaking ties. Match only when the larger physical-line count is no more than twice the smaller. Report unmatched flagged definitions and the resulting sizes, years and files. Do not silently use unflagged definitions from other files.

## Outcome

Reuse the exact candidate-commit rule and first-parent file-event ledger from `analysis/documented_fix_associations/PROTOCOL.md`. In Jenkins this requires a JENKINS issue identifier and a fix/regression term; in Tomcat an ASF Bugzilla identifier and a fix/correct/resolve term. Exclude reversions. For every qualifying `M` event of a matched baseline file lineage after the baseline commit and within its next 365 timestamp days, parse the *old blob* using the pinned Java grammar. Re-identify each matched definition by a unique `(path,symbol)` in that old version. Compare old and new blob lines. A body edit is a removed/replaced old line intersecting the old executable body, or an insertion anchored strictly inside it. A declaration-only change is retained separately. If a definition is missing or ambiguous at any candidate event for its lineage, mark its outcome unresolved rather than counting it as an unedited method. Exclude a pair if either outcome is unresolved. Different source paths on the same lineage can be followed only when unique method symbols remain; the path itself is recorded at each event. The outcome is binary: at least one qualifying body edit. A zero means no observed event under this documentary rule, not no bug.

## Estimation and reporting

Report candidate event and method-identification coverage, including skipped or unresolved outcomes. Report paired risks and their difference in percentage points for each repository. Estimate the paired difference using an intercept-only model over complete matched pairs, with two-way clustered covariance by file lineage and baseline year; the reference degrees of freedom is the smaller cluster count minus one. Report uncertainty as exploratory and do not pool repositories. Check robustness of the association to excluding pairs with a candidate file event at which another method could not be tracked. Repeat observations of a method across annual baselines are dependent and must not be described as independent entities. Describe existing source-checked God Class fixes separately because this Long Method analysis asks a different question.

## Interpretation

Exact body overlap improves localisation over the prior file-level outcome. It still cannot establish that the flagged method contained the reported defect, that complexity caused the defect, or that removing the finding would prevent future bugs. Large refactorings, overloaded names, history filtering, issue-label incompleteness, and unmatched files limit coverage. Freeze all source hashes, parser versions, matching decisions, event identities and analysis code; replay from a fresh output directory before publication.
